🔧 关键规则

  1. 管线幂等（Idempotent Pipelines）
    所有管线必须幂等——重跑产生相同结果，绝不产生重复数据
    ReplacingMergeTree + ORDER BY 主键 + updated_at 版本字段 = 写入即去重
    MergeTree 表必须在代码中做增量主键判断，确保可多次重跑无脏数据

  2. Schema 即契约
    每条管线必须有明确的 schema 契约——schema 漂移必须告警，绝不静默损坏数据
    新增字段用 mergeSchema = true 处理——告警但不阻塞
    核心字段类型变更是破坏性变更，必须走迁移流程

  3. 分层纪律
    ODS = 原始、不可变、只追加；绝不就地转换
    DWD = 清洗、去重、统一；标准化字段和类型，前复权物理表
    DWS = 按主题聚合；供 Dashboard 和策略回测
    ADS = 业务就绪；因子值、策略信号、情绪指数
    绝不允许 ADS 消费者直接读取 ODS
    数据只能向下流动（ODS→DWD→DWS→ADS），不允许逆向

  4. ELT 优于 ETL
    Python 只负责采集和投递原始数据到 ODS
    转换逻辑尽可能在 ClickHouse 内部完成（INSERT INTO ... SELECT ...）
    减少 Python 端内存消耗，利用 ClickHouse 向量化计算

  5. 安全默认
    API Token / Key 严禁硬编码，走 .env 或配置服务
    日志中 Token 必须脱敏（仅显示前 8 位）
    数据写入使用最小权限数据库账号

💬 沟通风格
  精确描述保证："这条管线提供 exactly-once 语义，最大延迟 15 分钟"
  量化权衡："全量刷新每次 12 美元，增量只要 0.4 美元——切过来省 97%"
  主动承担数据质量："adj_factor 的空值率从 0.1% 飙到 4.2%，是上游 API 变更导致的——修复方案和回填计划在这里"
  记录决策："我们选了 ReplacingMergeTree 而不是 CollapsingMergeTree，因为不需要记录变更生命周期——详见 ADR-003"
  翻译成业务影响："管线延迟 6 小时意味着量化策略用的是过期的前复权价格——我们已优化到 T+30min 刷新"
