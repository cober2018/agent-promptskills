# 业务架构

## 概述

企业做什么？为谁创造价值？业务如何运转？**业务架构是连接战略与技术的桥梁——没有它，所有技术决策都是自嗨。**

## 何时使用

- 新业务线从 0 到 1 梳理
- 业务能力地图构建（三级分类 + Owner）
- 价值流分析与瓶颈识别
- 事件风暴（Event Storming）梳理领域事件
- 组织结构与架构边界对齐（康威定律）
- 跨部门能力争议解决

**不要用于：** 系统设计和服务拆分（用 `application-architecture`）、数据建模（用 `data-architecture`）、技术选型（用 `technology-architecture`）。

## 职责范围

| 范畴 | 内容 |
|---|---|
| 价值流（Value Stream） | 从客户需求到价值交付的端到端流程 |
| 业务能力（Business Capability） | 企业「能做什么」的稳定抽象，不随组织结构变化 |
| 业务流程（Business Process） | 能力如何被编排成具体的运营活动 |
| 组织对齐（Org Alignment） | 团队边界如何与能力 / 价值流对齐（康威定律） |

## 业务能力地图（三级分类）

### 构建步骤

1. 从价值流出发，识别端到端交付所需的全部能力
2. 将能力按「核心 / 支撑 / 基础」三级分类
3. 为每个能力指定 Owner 团队
4. 映射到应用组件和数据域（与 `application-architecture`、`data-architecture` 联动）

### 三级分类原则

| 等级 | 定义 | 投资策略 | 技术选型倾向 | 电商示例 |
|---|---|---|---|---|
| 🎯 核心能力 | 直接创造差异化价值，构成竞争壁垒 | 自研为主，重点投入 | 深度定制，完全掌控 | 商品管理、交易履约、客户运营、供应链协同 |
| 🔧 支撑能力 | 必须做好但不构成差异化 | 自研 + 采购混合 | 优先成熟方案，适度定制 | 支付结算、风险控制、数据智能、客户服务 |
| 🏗️ 基础能力 | 行业通用，人人都需要 | 采购为主，避免重复造轮子 | SaaS / 开源优先 | 身份与访问、通知与消息、文件与存储、监控与审计 |

## 价值流分析

### 价值流映射模板

```
[触发事件] → [阶段 1] → [阶段 2] → ... → [价值交付]
              参与角色      参与角色
              处理时间      处理时间
              等待时间      等待时间
              痛点/瓶颈     痛点/瓶颈
```

### 关键度量

| 度量 | 含义 |
|---|---|
| 处理时间（Value-Adding Time） | 实际创造价值的时间 |
| 等待时间（Wait Time） | 排队、审批、等上游的时间 |
| 流动效率 | 处理时间 / (处理时间 + 等待时间) |

**目标：** 识别等待时间最长的环节，那就是优化的杠杆点。

### 示例：电商「从下单到收货」价值流

| 阶段 | 处理时间 | 等待时间 |
|---|---|---|
| 下单 | 200ms | 0 |
| 支付 | 3s | 0 |
| 拣货 | 30min | 10min ⚠️ |
| 发货 | 2h | 4h ⚠️ |
| 签收 | 1-3d | — |
| **合计** | **~2.5h** | **~4.2h** |

**瓶颈分析：** 流动效率 37%，拣货和发货环节的等待时间占总时间的 60%。

## 业务流程建模（事件风暴）

**流程：**

1. 识别领域事件（过去时态的业务事实）——「订单已创建」「支付已完成」
2. 回溯触发事件的命令——「提交订单」「确认支付」
3. 识别命令的发起者（角色 / 系统）
4. 发现聚合（处理命令、产生事件的业务实体）
5. 画出限界上下文边界
6. 识别上下文间的关系（上游 / 下游、事件流转）

**产出物：**
- 领域事件清单
- 命令清单
- 聚合及其不变量
- 限界上下文边界图
- 上下文映射关系（→ 交给 `application-architecture` 深化）

## 组织对齐与康威定律

**康威定律：** 系统设计会映射组织的沟通结构。

| ✅ 正确对齐的标志 | ❌ 危险信号 |
|---|---|
| 业务能力边界 ≈ 团队边界 ≈ 服务边界 ≈ 代码仓库边界 | 一个需求需要 3+ 个团队协同修改 → 边界划错了 |
| 团队可以独立决策、独立部署、独立演进 | 团队频繁跨边界沟通 → 考虑合并或重新划分 |
| 一个需求通常只需 1 个团队独立完成 | 服务边界和团队边界不一致 → 谁拥有这个服务？ |

**逆康威策略：** 先设计理想的架构边界，再调整组织结构去匹配（而不是让现有组织结构决定架构）。这需要管理层的支持和授权。

## 常见反模式

| 反模式 | 症状 | 解药 |
|---|---|---|
| 能力碎片化 | 同一个业务能力散落在 5 个团队中，没人负全责 | 明确能力 Owner，建立能力治理委员会 |
| 流程意大利面 | 流程间大量隐式依赖，改一处崩三处 | 用事件风暴梳理，显式化依赖关系 |
| PPT 架构师 | 画了漂亮的能力地图但从未落地到系统设计 | 每个能力必须映射到具体的应用组件和数据实体 |
| 组织驱动架构 | 「因为我们有这个部门，所以要有这个服务」 | 先梳理价值流，再决定组织结构 |
| 忽视非功能性业务需求 | 只关注功能流程，忽略合规、审计、风控等横切需求 | 将合规 / 风控作为一等公民纳入业务建模 |
| 假敏捷 | 有站会有迭代但没有真正的增量交付 | 按价值流拆分交付单元，每个迭代交付可验证的业务价值 |
