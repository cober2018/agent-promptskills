# 应用架构

## 概述

如何把业务能力拆解为可演进的应用系统。**应用架构的核心是边界——边界清晰才能独立演进。**

## 何时使用

- 系统从零设计或重大重构
- 服务边界争议、循环依赖、跨服务改造频繁
- 选型微服务 / 单体 / 事件驱动 / CQRS / BFF
- 集成策略（同步 RPC / 异步消息 / 事件）
- 写架构决策记录（ADR）
- Code Review 中的架构合规审查

**不要用于：** 业务能力地图与价值流（用 `business-architecture`）、数据库 Schema 设计（用 `database-engineering`）、CI/CD（用 `cicd-engineering`）。

## DDD 领域驱动设计

### 领域发现流程

1. 接收 `business-architecture` 事件风暴产出（领域事件、命令、聚合）
2. 细化限界上下文边界和职责
3. 定义聚合根、实体、值对象
4. 明确上下文间的映射关系
5. 设计领域事件的发布与消费机制

### 上下文映射模式（按自主权从高到低）

| 模式 | 适用 |
|---|---|
| 各行其道（Separate Ways） | 两个上下文完全独立，不做集成 |
| 防腐层（ACL） | 下游建立翻译层，隔离外部模型污染 |
| 开放主机服务（OHS） | 上游提供标准协议供多个下游使用 |
| 客户-供应商（Customer-Supplier） | 上游提供，下游消费，有明确 SLA |
| 合作关系（Partnership） | 两个团队共同演进，适合紧密协作的核心域 |
| 跟随者（Conformist） | 下游完全适配上游模型，放弃自主权 |

### 依赖方向检查

| ✅ 正确 | ❌ 危险信号 |
|---|---|
| UI → 应用 → 领域 → 基础设施（依赖倒置通过端口/适配器） | 领域层引用框架包（Spring、Django） |
| | 基础设施细节泄漏到 API 响应（数据库 ID 格式、内部错误栈） |
| | 两个服务互相直接调用（循环依赖） |

## 架构模式选型

| 模式 | 适用 | 不适用 | 关键点 |
|---|---|---|---|
| 模块化单体 | 小团队（≤ 3 个），边界不清晰，产品早期 | 需要独立扩展和部署 | 模块间通过接口通信，共享进程但不共享内部实现 |
| 微服务 | 领域清晰，需要团队自治和独立部署 | 小团队，产品早期 | 每个服务有明确 Owner、独立数据库、独立部署流水线 |
| 事件驱动 | 松耦合、异步工作流、跨系统集成 | 需要强一致性的场景 | 团队必须理解最终一致性，消费者必须幂等 |
| CQRS | 读写不对称，复杂查询场景 | 简单 CRUD | 接受读模型的数据延迟，团队能驾驭双模型复杂度 |
| BFF | 多端差异化，移动端和 Web 端需求不同 | 单一前端 | BFF 归前端团队所有，不要变成另一个通用后端 |
| Strangler Fig | 遗留系统渐进式替换 | 全新系统 | 新旧共存的过渡期需要代理层路由流量 |

**选型决策链：**

| 团队规模 | 决策 |
|---|---|
| ≤ 15 人 | 从模块化单体开始，别碰微服务 |
| > 15 人 + 领域边界清晰 | 微服务可行，但先确认每个服务有 Owner |
| > 15 人 + 领域边界不清晰 | 先做业务架构梳理，再谈拆分 |

## 集成策略

### 服务间通信决策树

| 同步响应？ | 一致性 | 推荐 |
|---|---|---|
| 是 | 强一致 | 同步 RPC（gRPC / REST）+ Saga |
| 是 | 最终一致可接受 | 同步 RPC + 本地缓存 + 优雅降级 |
| 否 | 不能丢失 | 持久化消息队列（Kafka / RabbitMQ）+ 至少一次投递 + 幂等消费者 |
| 否 | 可容忍丢失 | 内存消息（Redis Pub/Sub）或 webhook + 重试 |

### API 设计原则

| 场景 | 协议 | 形态 |
|---|---|---|
| 对外 API（前端 / 第三方） | RESTful | 版本化（/v1/），面向资源 |
| 服务间 API（内部） | gRPC（性能、类型）或 REST（简单） | IDL 驱动 |
| 异步集成 | 领域事件（CloudEvents 格式） | 消息队列投递 |
| 统一入口 | API 网关 | 认证、限流、路由、协议转换 |

## 架构决策记录（ADR）

**模板：**

```markdown
# ADR-XXX: [决策标题]

状态：提议中 / 已接受 / 已弃用 / 被 ADR-YYY 取代

## 背景
是什么问题促使我们做这个决策？当前的约束和上下文是什么？

## 决策
我们提出或实施的变更是什么？

## 备选方案
- 方案 A — 优点：... / 缺点：... / 风险：...
- 方案 B — 优点：... / 缺点：... / 风险：...

## 影响
- 这个变更使什么变得更容易？
- 使什么变得更难？
- 对其他架构层（业务 / 数据 / 技术）有什么影响？

## 关联
- 业务能力：关联到哪个业务能力？
- 数据影响：影响哪些数据域？
- 技术依赖：依赖哪些技术组件？
```

**使用规则：**
- 每个重大技术决策都必须有 ADR。
- ADR 一旦「已接受」就不修改，用新 ADR 取代旧 ADR。
- ADR 存放在代码仓库（`docs/adr/`），与代码同仓版本管理。
- 新团队成员入职必读 ADR，理解「为什么这样做」。

## 常见反模式

| 反模式 | 症状 | 解药 |
|---|---|---|
| 分布式单体 | 微服务之间同步调用链 > 3 层，一个服务改了其他全得改 | 用事件驱动解耦，或合并回单体 |
| 金锤子 | 所有问题都用同一个技术栈解决 | 按场景选型，允许多语言多框架（但控制种类数） |
| 简历驱动开发 | 选技术因为「想学」而非「合适」 | 用 ADR 强制记录选型理由 |
| 过早抽象 | 只有一个实现就搞了接口 + 工厂 + 策略 | 等到第三次重复再抽象（Rule of Three） |
| 共享数据库 | 多个服务直接读写同一个数据库 | 通过 API 或事件共享数据，每个服务拥有自己的数据 |
| 大泥球 | 没有明确的模块边界，任何代码改动都可能影响全局 | 先画依赖图，再逐步拆分 |
