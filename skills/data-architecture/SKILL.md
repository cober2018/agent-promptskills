# 数据架构

## 概述

数据如何建模？如何流转？如何治理？如何产生洞察？**数据架构是业务价值的天花板——没有良好的数据架构，再好的算法也是空中楼阁。**

## 何时使用

- 数据建模（概念 / 逻辑 / 物理模型）
- 数仓分层设计（ODS / DWD / DWS / ADS）
- 数据存储选型（OLTP / OLAP / 文档 / 图 / 时序 / 对象）
- 数据治理框架（质量 / 安全 / 血缘 / 合规）
- 指标体系设计（北极星 / 过程 / 操作指标）
- 跨域数据访问规范

**不要用于：** 实时管线开发（用 `pipeline-engineering`）、数据库 Schema 优化（用 `database-engineering`）、数据质量规则（用 `data-quality`）。

## 职责范围

| 范畴 | 内容 |
|---|---|
| 数据建模 | 概念模型、逻辑模型、物理模型；实体关系与数据标准 |

## 数据分域与 Owner

**原则：**

- 每个数据域有且仅有一个 Owner 团队。
- 数据域边界应与限界上下文对齐（与 `application-architecture` 联动）。
- 跨域数据访问通过 API / 事件 / 数据产品，不直接读库。

**示例（电商）：**

| 数据域 | Owner 团队 | 核心数据 |
|---|---|---|
| 客户域 | 用户增长团队 | 客户画像、行为数据、会员等级 |
| 商品域 | 商品中心团队 | 商品信息、类目体系、价格策略 |
| 交易域 | 交易平台团队 | 订单数据、支付流水、退换货 |
| 供应链域 | 供应链团队 | 库存数据、物流数据、供应商 |

**示例（量化 + 新媒体双线）：**

| 数据域 | Owner 团队 | 核心数据 |
|---|---|---|
| 行情域 | 数据工程 | 行情 K 线、复权因子、财务、指数成分 |
| 因子域 | 量化研究 | Alpha 因子值、IC 评估、因子定义 |
| 行为埋点域 | 新媒体运营 | 用户曝光 / 点击 / 转化 / 留存事件 |
| 实验域 | 新媒体运营 + 数据工程 | AB 实验分桶、SRM 监控、实验配置 |
| 用户域 | 新媒体运营 | 用户画像、会员等级、LTV、活跃度 |

**划分方法：**

1. 从业务能力地图出发（`business-architecture` 产出）
2. 识别每个能力域的核心数据实体
3. 确定实体的权威来源（谁产生、谁维护）
4. 以权威来源为依据划定数据域边界

## 数据建模三层架构

| 层级 | 产物 | 目的 | 决策 |
|---|---|---|---|
| 概念模型（业务人员能看懂） | 实体：客户、订单、商品；关系：客户-下单-订单 | 对齐业务语言，是业务和技术沟通的桥梁 | — |
| 逻辑模型（与技术无关） | 表 / 实体定义、属性、主外键、约束、3NF / 维度建模 | 确保数据完整性和一致性 | OLTP → 3NF；OLAP → 维度建模（星型 / 雪花） |
| 物理模型（特定技术实现） | 表结构、索引策略、分区方案、存储引擎、序列化格式 | 满足性能和运维需求 | 引擎选型、分区、索引、压缩 |

## 数据存储选型

| 数据特征 | 推荐 | 原因 | 不适合 |
|---|---|---|---|
| 事务性业务（订单、支付） | PostgreSQL / MySQL | 强一致性，ACID 事务 | 超大规模写入 |
| 高并发读缓存 | Redis | 亚毫秒延迟，丰富数据结构 | 持久化为主 |
| 文档型灵活 Schema | MongoDB | Schema 灵活，开发快 | 复杂多表 JOIN |
| 海量日志 / 事件分析 | ClickHouse / Elasticsearch | 列式存储，高压缩，快速聚合 | 高频事务更新 |
| 图关系数据 | Neo4j / TigerGraph | 复杂关系查询 O(1) 跳转 | 简单 KV 场景 |
| 时序数据（IoT / 监控） | TimescaleDB / InfluxDB | 时间分区，自动降采样 | 通用业务查询 |
| 海量对象存储 | S3 / OSS / MinIO | 无限扩展，低成本 | 低延迟查询 |

**选型决策框架：** 先明确读写比例、一致性要求、查询模式 → 再看团队熟悉度和运维能力 → 最后考虑成本和扩展性。差距不大时选团队最熟的。

## 数据仓库分层设计

```
ADS（应用数据层）
  面向特定应用场景的数据集（营销人群包、风控特征集、报表数据）
  ↑
DWS（数据服务层 / 汇总层）
  按主题域聚合的宽表（用户行为日汇总、商品销售周汇总）
  ↑
DWD（明细数据层）
  清洗、标准化后的事实明细（订单明细事实表、用户行为明细表）
  ↑
DIM（维度层）
  一致性维度，跨主题域共享（用户维度、商品维度、时间维度、地区维度）
  ↑
ODS（操作数据层）
  原始数据的忠实副本，不做加工（MySQL binlog、日志文件原始导入）
```

**数据流向：** ODS → DWD → DWS → ADS

**加工原则：**

- 逐层加工，禁止跨层引用（ODS 直接到 ADS = 反模式）。
- 每层有明确职责，不要把清洗逻辑放到汇总层。
- 维度表独立管理，确保跨主题域的一致性。

## 数据治理框架

### 1. 数据质量

| 维度 | 定义 |
|---|---|
| 完整性 | 必填字段不为空 |
| 准确性 | 数据与事实一致 |
| 一致性 | 同一数据在不同系统中语义一致 |
| 时效性 | 数据在 SLA 时间内可用 |
| 唯一性 | 无不合理的重复记录 |

### 2. 数据安全

- **分类分级：** 公开 / 内部 / 敏感 / 机密。
- **脱敏策略：** 动态脱敏（查询时） vs 静态脱敏（导出时）。
- **访问控制：** RBAC + ABAC，最小权限原则。
- **加密方案：** 传输加密（TLS）+ 存储加密（AES-256）。

### 3. 数据血缘

- 字段级血缘追踪：从报表字段追溯到源头表和字段。
- 影响分析：修改上游表结构时，自动识别下游影响范围。
- 数据目录：可搜索的元数据中心（数据描述、Owner、SLA）。

### 4. 数据合规

- GDPR / 个人信息保护法的数据主体权利（访问、删除、可携带）。
- 数据留存策略：各类数据的保留期限和清除机制。
- 审计日志：谁在什么时间访问 / 修改了什么数据。

## 指标体系设计

| 层级 | 名称 | 示例 |
|---|---|---|
| L1 | 北极星指标（公司级） | DAU、GMV、NPS |
| L2 | 过程指标（部门级） | 转化率、客单价、复购率 |
| L3 | 操作指标（团队级） | 页面加载时间、接口成功率、工单响应时间 |

**指标定义规范：**

- 每个指标必须有唯一中文名、英文名、口径定义。
- 口径定义包括：计算公式、数据来源、统计周期、过滤条件。
- 同一指标在所有报表 / 系统中使用同一计算逻辑。
- 变更口径时必须通知所有消费方。

**跨业务线指标示例：**

| 业务线 | L1 北极星 | L2 过程 | L3 操作 |
|---|---|---|---|
| 量化投研 | 策略年化收益 / 最大回撤 | 因子 Rank IC、IR、换手率 | 数据延迟 p95、回测偏差 |
| 新媒体运营 | 月活 MAU、内容曝光 | 转化率、互动率、涨粉率、CTR | 平台分发量、AB 实验分桶偏移 SRM |
| 商业化 | GMV、广告 ROI | 客单价、复购率、CAC | 加购转化率、漏斗各层流失率 |
| 用户资产 | LTV 90 / LTV 365 | 次日 / 7 日 / 30 日留存 | 注册漏斗、激活漏斗 |

## 多级缓存与文件存储抽象

**分层缓存模型：**

| 层级 | 存储 | 适用 | TTL | 一致性策略 |
|---|---|---|---|---|
| L1 本地缓存 | Caffeine / Guava | 热点配置、字典、用户画像 | 30s ~ 5min | 过期失效 + 版本号失效 |
| L2 分布式缓存 | Redis | 跨实例共享、热点时序数据 | 1min ~ 48h | Cache-Aside + TTL |
| L3 持久化层 | 数据库 / 对象存储 | 全量真实数据 | 永久 | — |

**文件系统抽象层：**

- 底层文件存储（S3 / OSS / HDFS / 本地磁盘）通过统一接口封装，对上层屏蔽分片、副本、压缩、路径拼接等细节。
- 抽象层最小接口：`read(path) / write(path, stream) / list(prefix) / delete(path) / exists(path)`。
- 路径命名规范：`{业务域}/{主题}/{数据粒度}/{分区}/file.{format}`（如 `quant/dwd/astock_daily/2025-01/file.parquet`）。
- 大文件写入采用分片 + 断点续传；小文件合并后再上传，避免海量小文件拖垮对象存储。
- 所有读路径必须走缓存（本地 + 分布式），原始 IO 仅作为冷数据兜底。

**容量 / 吞吐 / 成本三角平衡：**

- 容量压力 → 加对象存储冷归档层 + 压缩（Parquet / ZSTD）。
- 吞吐压力 → 加本地缓存层 + 异步预热，避免回源击穿数据库。
- 成本压力 → 热数据 SSD、温数据 HDD / 标准对象存储、冷数据归档存储（Glacier / 归档 OSS）。

## 常见反模式

| 反模式 | 症状 | 解药 |
|---|---|---|
| 数据孤岛 | 同一实体在 5 个系统中有 5 种定义 | 建立主数据管理（MDM），统一数据标准 |
| ETL 地狱 | 数百条 ETL 管线互相依赖，没人敢改 | 引入数据血缘工具，逐步迁移到 ELT + dbt |
| 万能大宽表 | 一张表 200 个字段，什么都有 | 按主题域拆分，遵循维度建模规范 |
| 读写混用 | 分析查询直接打到生产库，导致线上抖动 | CQRS 分离，分析走读副本或数仓 |
| 指标口径混乱 | 「日活」在 3 个报表中有 3 个不同数字 | 建立指标中心，统一口径定义和计算逻辑 |
| Schema 恐惧症 | 所有数据都扔 JSON 里「保持灵活」 | 核心实体用强 Schema，仅扩展属性用 JSON |
