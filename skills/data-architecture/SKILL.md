💾 数据架构（Data Architecture）
核心问题：数据如何建模？如何流转？如何治理？如何产生洞察？


📌 职责范围
  数据建模（Data Modeling）   ——  概念模型、逻辑模型、物理模型；实体关系与数据标准
  数据流转（Data Flow）      ——  数据从产生到消费的全链路；ETL/ELT、CDC、实时流
  数据治理（Data Governance） ——  数据质量、数据安全、数据目录、血缘追踪、合规
  数据分析（Data Analytics）  ——  数仓分层、指标体系、自助分析、AI/ML 数据管线


📌 数据分域与数据 Owner

  原则：
    每个数据域有且仅有一个 Owner 团队
    数据域边界应与限界上下文对齐（与应用架构 Skill 联动）
    跨域数据访问通过 API / 事件 / 数据产品，不直接读库

  示例（电商）：
    客户域（Owner: 用户增长团队）：客户画像、行为数据、会员等级
    商品域（Owner: 商品中心团队）：商品信息、类目体系、价格策略
    交易域（Owner: 交易平台团队）：订单数据、支付流水、退换货
    供应链域（Owner: 供应链团队）：库存数据、物流数据、供应商

  划分方法：
  1. 从业务能力地图出发（业务架构 Skill 产出）
  2. 识别每个能力域的核心数据实体
  3. 确定实体的权威来源（谁产生、谁维护）
  4. 以权威来源为依据划定数据域边界


📌 数据建模三层架构

  概念模型（业务人员能看懂）
    实体：客户、订单、商品
    关系：客户-下单-订单、订单-包含-商品
    目的：对齐业务语言，是业务和技术沟通的桥梁
        ↓
  逻辑模型（与技术无关的数据结构）
    表/实体定义、属性、数据类型
    主键、外键、约束
    范式化设计（3NF）或维度建模（星型/雪花）
    目的：确保数据完整性和一致性
        ↓
  物理模型（特定技术平台的实现）
    表结构、索引策略、分区方案
    存储引擎选择、序列化格式
    目的：满足性能和运维需求

  建模决策：
    OLTP 场景（业务系统）→ 3NF 范式化，减少冗余，保证一致性
    OLAP 场景（分析系统）→ 维度建模（Kimball），宽表，优化查询性能
    混合场景 → OLTP 用范式化，通过 ETL/CDC 同步到 OLAP 用维度建模


📌 数据存储选型

  事务性业务数据（订单、支付）
    推荐：PostgreSQL / MySQL
    原因：强一致性，ACID 事务
    不适合：超大规模写入

  高并发读缓存
    推荐：Redis
    原因：亚毫秒延迟，丰富数据结构
    不适合：持久化为主的场景

  文档型灵活 Schema
    推荐：MongoDB
    原因：Schema 灵活，开发快
    不适合：复杂多表 JOIN

  海量日志/事件分析
    推荐：ClickHouse / Elasticsearch
    原因：列式存储，高压缩，快速聚合
    不适合：高频事务更新

  图关系数据
    推荐：Neo4j / TigerGraph
    原因：复杂关系查询 O(1) 跳转
    不适合：简单 KV 场景

  时序数据（IoT/监控）
    推荐：TimescaleDB / InfluxDB
    原因：时间分区，自动降采样
    不适合：通用业务查询

  海量对象存储
    推荐：S3 / OSS / MinIO
    原因：无限扩展，低成本
    不适合：需要低延迟查询

  选型决策框架：
    先明确数据的读写比例、一致性要求、查询模式
    再看团队熟悉度和运维能力
    最后考虑成本和扩展性
    差距不大时，选团队最熟的


📌 数据仓库分层设计

  ADS（应用数据层）
    面向特定应用场景的数据集
    例：营销人群包、风控特征集、报表数据
      ↑
  DWS（数据服务层/汇总层）
    按主题域聚合的宽表
    例：用户行为日汇总、商品销售周汇总
      ↑
  DWD（明细数据层）
    清洗、标准化后的事实明细
    例：订单明细事实表、用户行为明细表
      ↑
  DIM（维度层）
    一致性维度，跨主题域共享
    例：用户维度、商品维度、时间维度、地区维度
      ↑
  ODS（操作数据层）
    原始数据的忠实副本，不做加工
    例：MySQL binlog 同步、日志文件原始导入

  数据流向：ODS → DWD → DWS → ADS
  加工原则：
    逐层加工，禁止跨层引用（ODS 直接到 ADS = 反模式）
    每层有明确的职责，不要把清洗逻辑放到汇总层
    维度表独立管理，确保跨主题域的一致性


📌 数据治理框架

  1. 数据质量
    完整性：必填字段不为空
    准确性：数据与事实一致
    一致性：同一数据在不同系统中语义一致
    时效性：数据在 SLA 时间内可用
    唯一性：无不合理的重复记录

  2. 数据安全
    分类分级：公开 / 内部 / 敏感 / 机密
    脱敏策略：动态脱敏（查询时）vs 静态脱敏（导出时）
    访问控制：RBAC + ABAC，最小权限原则
    加密方案：传输加密（TLS）+ 存储加密（AES-256）

  3. 数据血缘
    字段级血缘追踪：从报表字段追溯到源头表和字段
    影响分析：修改上游表结构时，自动识别下游影响范围
    数据目录：可搜索的元数据中心，包含数据描述、Owner、SLA

  4. 数据合规
    GDPR / 个人信息保护法的数据主体权利（访问、删除、可携带）
    数据留存策略：各类数据的保留期限和清除机制
    审计日志：谁在什么时间访问/修改了什么数据


📌 指标体系设计

  指标分层：
    L1 北极星指标（公司级）：DAU、GMV、NPS
    L2 过程指标（部门级）：转化率、客单价、复购率
    L3 操作指标（团队级）：页面加载时间、接口成功率、工单响应时间

  指标定义规范：
    每个指标必须有唯一的中文名、英文名、口径定义
    口径定义包括：计算公式、数据来源、统计周期、过滤条件
    同一个指标在所有报表/系统中使用同一个计算逻辑
    变更口径时必须通知所有消费方


📌 数据架构反模式

  数据孤岛
    症状：同一实体（如"客户"）在 5 个系统中有 5 种定义
    解药：建立主数据管理（MDM），统一数据标准

  ETL 地狱
    症状：数百条 ETL 管线互相依赖，没人敢改
    解药：引入数据血缘工具，逐步迁移到 ELT + dbt

  万能大宽表
    症状：一张表 200 个字段，"什么都有"
    解药：按主题域拆分，遵循维度建模规范

  读写混用
    症状：分析查询直接打到生产库，导致线上抖动
    解药：CQRS 分离，分析走读副本或数仓

  指标口径混乱
    症状："日活"在 3 个报表中有 3 个不同的数字
    解药：建立指标中心，统一口径定义和计算逻辑

  Schema 恐惧症
    症状：所有数据都扔 JSON 里"保持灵活"，查询成噩梦
    解药：核心实体用强 Schema，仅扩展属性用 JSON
