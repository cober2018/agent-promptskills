🛡️ 系统可靠性（System Reliability）
核心问题：系统怎么跑得稳？怎么发现问题？怎么快速恢复？


📌 性能调优

  性能分析流程（先量后优化）：
    1. 定义目标：p95 < 200ms、p99 < 500ms、QPS > 1000
    2. 建立基线：当前性能数据是什么
    3. 识别瓶颈：用数据定位，不要猜
    4. 优化瓶颈：一次只改一个变量
    5. 验证效果：对比优化前后的数据
    6. 重复：直到达到目标或投入产出比不值得

  常见瓶颈定位：

    CPU 高：
      看火焰图（flamegraph），找哪个函数占用最多
      常见原因：JSON 序列化/反序列化、正则表达式、加密计算
      解法：算法优化、异步化、缓存计算结果

    内存高：
      看堆内存分布，找大对象和泄漏
      常见原因：大列表一次性加载到内存、全局缓存无上限、连接池泄漏
      解法：流式处理、设置缓存上限和 LRU 淘汰、连接池监控

    I/O 高（最常见）：
      数据库查询慢 → 看慢查询日志和执行计划
      网络调用慢 → 看外部依赖的延迟分布
      磁盘 I/O → 看是否有大量日志写入或临时文件
      解法：索引优化、连接池、批量操作、缓存

    GC 频繁（JVM / Go / Node.js）：
      看 GC 暂停时间和频率
      常见原因：大量短生命周期对象、堆内存不够
      解法：减少对象分配、调整 GC 参数、对象池

  应用层优化清单：
    数据库：N+1 消除、索引优化、连接池调参
    缓存：热数据缓存、查询结果缓存、计算结果缓存
    网络：减少调用次数（批量化）、压缩响应体（gzip/br）、连接复用（keep-alive）
    计算：异步化非关键路径、并行化独立任务、预计算
    序列化：选择高效格式（Protobuf > JSON > XML）


📌 监控与告警

  监控三层模型：

    基础设施层（系统级）：
      CPU 使用率、内存使用率、磁盘 I/O、网络流量
      容器 / Pod 状态、节点健康
      数据来源：Prometheus node_exporter、cAdvisor

    应用层（服务级）：
      请求量（QPS）、延迟分布（p50/p95/p99）、错误率
      连接池使用率、队列深度、线程池使用率
      数据来源：应用内埋点、中间件指标

    业务层（价值级）：
      订单量、支付成功率、注册转化率
      核心流程的端到端成功率和耗时
      数据来源：业务埋点、日志聚合

  埋点规范：

    每个 API 端点必须采集（自动化，不需要手动加）：
      请求计数（按状态码分组）
      延迟分布（直方图，看 p50/p95/p99）
      错误计数（按错误类型分组）

    每个外部依赖调用必须采集：
      调用计数、延迟、错误率
      熔断器状态

    关键业务操作手动埋点：
      操作计数
      成功/失败分组
      业务相关的维度标签

  告警设计：

    告警分级：
      P0（立即响应）：核心服务不可用、数据一致性问题、安全事件
      P1（1小时内）：非核心服务异常、性能严重退化、错误率飙升
      P2（当天内）：性能轻微退化、磁盘空间预警、证书即将过期
      P3（本周内）：性能优化建议、资源使用趋势预警

    告警规则设计原则：
      基于 SLO 告警，不是基于资源阈值
        ❌ CPU > 80% 告警（可能没有任何影响）
        ✅ p99 延迟 > 500ms 持续 5 分钟告警（用户体验受损）
      设置告警窗口，避免瞬时抖动触发
        ❌ 错误率 > 1% 立即告警
        ✅ 错误率 > 1% 持续 3 分钟告警
      每条告警必须有 Runbook（收到告警后怎么处理）
      定期清理无效告警，告警数量以"少而精"为目标


📌 安全加固

  输入安全：
    SQL 注入防护：参数化查询，永远不拼接 SQL 字符串
    XSS 防护：输出时转义 HTML 实体，CSP 头限制脚本执行
    SSRF 防护：限制内部网络访问，URL 白名单校验
    文件上传：校验文件类型（不信任扩展名，检查 magic bytes）、限制大小、隔离存储
    JSON 解析：限制深度和大小，防止 JSON bomb

  HTTP 安全头：
    Strict-Transport-Security → 强制 HTTPS
    X-Content-Type-Options: nosniff → 防止 MIME 类型嗅探
    X-Frame-Options: DENY → 防止点击劫持
    Content-Security-Policy → 限制资源加载来源
    X-XSS-Protection: 0 → 禁用浏览器的有 bug 的 XSS 过滤器
    Referrer-Policy: strict-origin-when-cross-origin → 控制 Referer 泄漏

  密码安全：
    哈希算法：bcrypt（成本因子 ≥ 12）或 argon2id
    绝不用 MD5、SHA-1、SHA-256（太快，容易暴力破解）
    密码强度要求：≥ 8 字符，检查是否在常见泄漏密码库中
    登录失败锁定：5 次失败后锁定 15 分钟（按 IP + 账号组合）

  敏感数据处理：
    数据库中：密码哈希存储、敏感字段加密存储
    日志中：密码、Token、身份证号、银行卡号绝不打印
    API 响应中：密码字段不返回，身份证/手机号脱敏显示
    传输中：全链路 TLS 1.2+，内部服务间 mTLS


📌 负载测试

  测试类型：
    基准测试（Benchmark）：正常负载下的性能数据，建立基线
    负载测试（Load Test）：逐步增加到预期峰值负载，验证系统承载能力
    压力测试（Stress Test）：超过设计容量，找到系统的极限和瓶颈
    浸泡测试（Soak Test）：长时间稳定负载，发现内存泄漏等慢性问题

  测试流程：
    1. 确定场景：哪些接口、什么比例、什么数据
    2. 准备环境：和生产环境尽量一致的测试环境
    3. 准备数据：足够量的测试数据（不是空库测试）
    4. 逐步加压：从 10% 预期负载开始，每次增加 20-30%
    5. 观察指标：QPS、延迟（p50/p95/p99）、错误率、资源使用率
    6. 找到拐点：延迟开始指数级上升的点就是系统瓶颈
    7. 输出报告：瓶颈在哪、最大承载量、优化建议

  工具选择：
    k6：适合开发者，用 JavaScript 写脚本，集成 CI 方便
    wrk / wrk2：轻量级 HTTP 压测，适合单接口快速测试
    Locust：Python 生态，支持分布式压测
    JMeter：功能全面但学习曲线陡，适合复杂场景


📌 部署策略

  滚动更新（Rolling Update）：
    逐步替换旧实例，最简单
    配置：maxSurge=25%, maxUnavailable=25%
    适用：无状态服务、大多数场景
    注意：确保新旧版本可以同时运行（向后兼容）

  蓝绿部署（Blue-Green）：
    两套完整环境，切流量一步到位
    回滚：切回旧环境，秒级回滚
    适用：对回滚速度要求极高的场景
    代价：资源消耗翻倍

  金丝雀发布（Canary）：
    先导 1-5% 流量到新版本，观察指标
    指标正常 → 逐步放量（10% → 30% → 50% → 100%）
    指标异常 → 自动回滚
    适用：核心服务、大规模用户
    配合：自动化指标检测 + 自动回滚

  特性开关（Feature Flag）：
    代码层面的功能开关，部署和发布解耦
    可以按用户、百分比、条件开关功能
    适用：灰度测试、A/B 测试、紧急关闭有问题的功能
    注意：开关用完要清理，避免开关债务


📌 故障排查

  故障响应流程：
    1. 确认影响范围：哪些服务、哪些用户、影响程度
    2. 止血：先恢复服务，再找根因
       回滚最近的发布
       切换到降级模式
       扩容应对流量
    3. 定位根因：
       看告警和监控面板 → 缩小范围
       看错误日志 → 找具体报错
       用 traceId 追踪请求链路 → 找到失败节点
    4. 修复并验证
    5. 写事后复盘（Postmortem）

  事后复盘模板：
    事件概要：什么时间、影响了什么、持续多久
    时间线：从发现到恢复的每个关键动作和时间点
    根因分析：直接原因 + 根本原因（用 5 Whys）
    修复措施：已做的和计划做的
    经验教训：我们学到了什么、如何防止再次发生
    行动项：具体的改进任务、责任人、截止日期

  常见故障模式速查：
    全链路超时 → 检查下游依赖是否故障或过载
    部分请求失败 → 检查是否有节点不健康（负载均衡问题）
    内存持续增长 → 检查是否有内存泄漏（连接未关闭、缓存无上限）
    数据库连接耗尽 → 检查连接池配置、是否有慢查询长时间占用连接
    消息堆积 → 检查消费者是否正常、消费速度是否跟得上
    CPU 打满 → 看火焰图找热点函数，检查是否有死循环或计算密集操作
