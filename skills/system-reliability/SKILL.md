🛡️ 系统可靠性（System Reliability）
核心问题：系统怎么跑得稳？怎么发现问题？怎么快速恢复？


📌 Go 并发与线程安全加固

  1. 协程泄露与死锁防范（Goroutine Leaks & Deadlocks）：
    - 每一个开启的 Goroutine 必须有明确的退出机制。使用 `context.Context` 透传取消信号，或通过专门的关闭 Channel 广播退出。
    - 严防 Channel 阻塞死锁：向无缓冲 Channel 发送数据或从无缓冲 Channel 接收数据时，必须配有 `select` 超时控制，防止协程永久挂起。
      ```go
      select {
      case ch <- data:
      case <-ctx.Done():
          // 优雅退出，防止协程泄露
      }
      ```

  2. 互斥锁与读写锁规范（Mutex / RWMutex）：
    - 锁的粒度应尽可能小，且绝不在持有锁的临界区内进行耗时的网络/磁盘 I/O 操作。
    - `lock.Lock()` 必须紧跟 `defer lock.Unlock()`，避免发生异常时未释放锁导致全局死锁。
    - 并发安全的单例模式：必须使用 `sync.Once`，严防 speculative 双重检查锁（Double-checked Locking）引发的竞态条件。


📌 Redis 缓存弹性与分布式锁

  1. 缓存穿透、击穿与雪崩防御（Cache Resilience）：
    - **防击穿 (Hotspot Key)**：在高频热点数据失效瞬间，使用单机互斥锁（Go 的 `singleflight`）或 Redis 分布式锁，仅放行一个请求去数据库重构缓存，其他请求原地等待结果，保护数据库不被打垮。
    - **防穿透 (Non-existent Key)**：对于不存在的 Key，在 Redis 中缓存空值或特殊标记（如 `"{}"`），设置 1-3 分钟超短 TTL，或在入口配置布隆过滤器（Bloom Filter）。
    - **防雪崩 (Mass Expiry)**：设置 Key 过期时间时，必须加上随机扰动值（如 `TTL + rand(0, 300s)`），避免海量数据在同一秒集体过期。

  2. 高可用分布式锁机制：
    - 使用 `SET key value NX PX 5000`（原子化创建 + 独占 + 5秒过期）获取锁，value 必须为每个实例/协程唯一的随机 UUID，防止“误删他人的锁”。
    - 释放锁必须使用 Lua 脚本，确保“校验 UUID 相同”与“物理删除 Key”是原子操作。
    - 针对长时间运行任务，必须配置锁续期（Watchdog 守护协程）机制，避免任务未完、锁提前过期导致并发双发。


📌 API 认证与防刷加固（API Throttling）

  1. Token 生命周期与续签安全：
    - JWT 访问 Token（Access Token）寿命控制在 15-30 分钟，刷新 Token（Refresh Token）寿命在 7-30 天且强制走 HttpOnly/Secure 存储，防止 XSS 窃取。
    - 每一个 Token 在服务端 Redis 中建立注销黑名单映射，支持用户强制登出或被管理员封禁时即刻作废。

  2. 智能限流保护（Throttling）：
    - 接口入口拦截：核心操作接口（如回测启动、资金结算、验证码发送）配置滑窗限流或令牌桶限流。
    - 限流返回：触发限流时返回 `HTTP 429 Too Many Requests`，并在 Header 中附带 `Retry-After: 60` 指示等待秒数。


📌 性能调优

  性能分析流程（先量后优化）：
    1. 定义目标：p95 < 100ms、p99 < 300ms、QPS > 1000
    2. 建立基线：当前性能数据是什么
    3. 识别瓶颈：用数据定位，不要猜
    4. 优化瓶颈：一次只改一个变量
    5. 验证效果：对比优化前后的数据
    6. 重复：直到达到目标或投入产出比不值得

  常见瓶颈定位：

    CPU 高：
      看火焰图（flamegraph），找哪个函数占用最多
      常见原因：JSON 序列化/反序列化、正则表达式、加密计算、Go 大量小对象频繁分配
      解法：算法优化、异步化、缓存计算结果、使用 `sync.Pool` 复用高频临时对象

    内存高：
      看堆内存分布，找大对象和泄漏
      常见原因：大列表一次性加载到内存、全局缓存无上限、连接池泄漏、Go channel未关闭导致协程悬挂
      解法：流式处理、设置缓存上限和 LRU 淘汰、连接池监控

    I/O 高（最常见）：
      数据库查询慢 → 看慢查询日志和执行计划
      网络调用慢 → 看外部依赖的延迟分布
      磁盘 I/O → 看是否有大量日志写入或临时文件
      解法：索引优化、连接池、批量操作、缓存

    GC 频繁：
      看 GC 暂停时间和频率
      常见原因：大量短生命周期对象、堆内存不够
      解法：减少对象分配、调整 GC 参数、对象池复用

📌 安全加固

  输入安全：
    SQL 注入防护：参数化查询，永远不拼接 SQL 字符串
    XSS 防护：输出时转义 HTML 实体，CSP 头限制脚本执行
    SSRF 防护：限制内部网络访问，URL 白名单校验
    文件上传：校验文件类型（不信任扩展名，检查 magic bytes）、限制大小、隔离存储
    JSON 解析：限制深度和大小，防止 JSON bomb

  HTTP 安全头：
    Strict-Transport-Security → 强制 HTTPS
    X-Content-Type-Options: nosniff → 防止 MIME 类型嗅探
    X-Frame-Options: DENY → 防止点击劫持
    Content-Security-Policy → 限制资源加载来源
    X-XSS-Protection: 0 → 禁用浏览器的有 bug 的 XSS 过滤器
    Referrer-Policy: strict-origin-when-cross-origin → 控制 Referer 泄漏

  密码安全：
    哈希算法：bcrypt（成本因子 ≥ 12）或 argon2id
    绝不用 MD5、SHA-1、SHA-256（太快，容易暴力破解）
    密码强度要求：≥ 8 字符，检查是否在常见泄漏密码库中
    登录失败锁定：5 次失败后锁定 15 分钟（按 IP + 账号组合）

  敏感数据处理：
    数据库中：密码哈希存储、敏感字段加密存储
    日志中：密码、Token、身份证号、银行卡号绝不打印
    API 响应中：密码字段不返回，身份证/手机号脱敏显示
    传输中：全链路 TLS 1.2+，内部服务间 mTLS


📌 负载测试

  测试类型：
    基准测试（Benchmark）：正常负载下的性能数据，建立基线
    负载测试（Load Test）：逐步增加到预期峰值负载，验证系统承载能力
    压力测试（Stress Test）：超过设计容量，找到系统的极限和瓶颈
    浸泡测试（Soak Test）：长时间稳定负载，发现内存泄漏等慢性问题

  测试流程：
    1. 确定场景：哪些接口、什么比例、什么数据
    2. 准备环境：和生产环境尽量一致的测试环境
    3. 准备数据：足够量的测试数据（不是空库测试）
    4. 逐步加压：从 10% 预期负载开始，每次增加 20-30%
    5. 观察指标：QPS、延迟（p50/p95/p99）、错误率、资源使用率
    6. 找到拐点：延迟开始指数级上升的点就是系统瓶颈
    7. 输出报告：瓶颈在哪、最大承载量、优化建议

📌 故障排查

  故障响应流程：
    1. 确认影响范围：哪些服务、哪些用户、影响程度
    2. 止血：先恢复服务，再找根因
       回滚最近的发布
       切换到降级模式
       扩容应对流量
    3. 定位根因：
       看告警和监控面板 → 缩小范围
       看错误日志 → 找具体报错
       用 traceId 追踪请求链路 → 找到失败节点
    4. 修复并验证
    5. 写事后复盘（Postmortem）
