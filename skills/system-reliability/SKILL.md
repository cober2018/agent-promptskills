# 系统可靠性

## 概述

系统怎么跑得稳？怎么发现问题？怎么快速恢复？**可靠性不是救火，而是把"崩"挡在前面。**

## 何时使用

- Go 协程并发安全（Goroutine 泄露、Channel 死锁、互斥锁）
- Redis 缓存防御（穿透 / 击穿 / 雪崩）与分布式锁
- API 认证防刷（Token 生命周期、限流）
- 性能调优（CPU / 内存 / I/O / GC 分析）
- 安全加固（输入校验、HTTP 头、密码、敏感数据）
- 负载测试（基准 / 负载 / 压力 / 浸泡）
- 故障排查流程

**不要用于：** 监控告警体系搭建（用 `observability-ops`）、CI/CD 流水线（用 `cicd-engineering`）、架构层面的可靠性设计（SLI/SLO/SLA 框架用 `technology-architecture`）。

## Go 并发与线程安全

### 1. 协程泄露与死锁防范

| 原则 | 说明 |
|---|---|
| 退出机制 | 每一个开启的 Goroutine 必须有明确的退出机制（`context.Context` 透传取消或专门的关闭 Channel） |
| Channel 超时 | 向无缓冲 Channel 发送或从无缓冲 Channel 接收时，必须配 `select` 超时控制，防止协程永久挂起 |

```go
select {
case ch <- data:
case <-ctx.Done():
    // 优雅退出，防止协程泄露
}
```

### 2. 互斥锁与读写锁规范

| 原则 | 说明 |
|---|---|
| 锁粒度 | 锁的粒度应尽可能小，绝不在持有锁的临界区内进行耗时的网络 / 磁盘 I/O |
| defer 释放 | `lock.Lock()` 必须紧跟 `defer lock.Unlock()`，避免异常时未释放锁导致全局死锁 |
| 并发安全单例 | 必须使用 `sync.Once`，严防 Double-checked Locking 引发的竞态条件 |

## Redis 缓存弹性与分布式锁

### 1. 缓存穿透 / 击穿 / 雪崩防御

| 现象 | 防御手段 |
|---|---|
| **击穿（Hotspot Key）** | 高频热点数据失效瞬间，使用单机互斥锁（Go `singleflight`）或 Redis 分布式锁，仅放行一个请求重构缓存 |
| **穿透（Non-existent Key）** | 不存在的 Key 缓存空值或特殊标记（如 `"{}"`），TTL 1-3 分钟；或入口配置布隆过滤器（Bloom Filter） |
| **雪崩（Mass Expiry）** | Key 过期时间必须加随机扰动（`TTL + rand(0, 300s)`），避免海量数据同一秒集体过期 |

### 2. 高可用分布式锁

| 步骤 | 实现 |
|---|---|
| 获取锁 | `SET key value NX PX 5000`（原子化创建 + 独占 + 5 秒过期） |
| value 唯一性 | 必须为每个实例 / 协程唯一的随机 UUID，防止"误删他人的锁" |
| 释放锁 | 必须使用 Lua 脚本，确保"校验 UUID 相同"与"物理删除 Key"是原子操作 |
| 锁续期 | 长时间运行任务必须配置 Watchdog 守护协程续期，避免任务未完、锁提前过期导致并发双发 |

## API 认证与防刷

### 1. Token 生命周期

| 元素 | 规范 |
|---|---|
| Access Token 寿命 | 15-30 分钟 |
| Refresh Token 寿命 | 7-30 天，强制 HttpOnly / Secure 存储 |
| 注销黑名单 | 每一个 Token 在服务端 Redis 中建立注销黑名单映射，支持用户强制登出或被管理员封禁时即刻作废 |

### 2. 智能限流（Throttling）

| 原则 | 实现 |
|---|---|
| 入口拦截 | 核心操作接口（回测启动、资金结算、验证码发送）配置滑窗限流或令牌桶限流 |
| 限流返回 | 触发限流时返回 `HTTP 429 Too Many Requests`，Header 附带 `Retry-After: 60` 指示等待秒数 |

## 性能调优

### 性能分析流程（先量后优化）

1. 定义目标：p95 < 100ms、p99 < 300ms、QPS > 1000
2. 建立基线：当前性能数据是什么
3. 识别瓶颈：用数据定位，不要猜
4. 优化瓶颈：一次只改一个变量
5. 验证效果：对比优化前后的数据
6. 重复：直到达到目标或投入产出比不值得

### 常见瓶颈定位

| 瓶颈类型 | 定位方法 | 常见原因 | 解法 |
|---|---|---|---|
| **CPU 高** | 火焰图（flamegraph） | JSON 序列化、正则、加密、Go 大量小对象分配 | 算法优化、异步化、缓存计算结果、`sync.Pool` 复用 |
| **内存高** | 堆内存分布 | 大列表一次性加载、全局缓存无上限、连接池泄漏、Channel 未关闭 | 流式处理、LRU 淘汰、连接池监控 |
| **I/O 高** | 慢查询日志 / 网络延迟分布 | DB 查询慢、依赖服务慢、磁盘日志写 | 索引优化、连接池、批量操作、缓存 |
| **GC 频繁** | GC 暂停时间和频率 | 大量短生命周期对象、堆内存不够 | 减少对象分配、调整 GC 参数、对象池复用 |

## 安全加固

### 输入安全

| 攻击向量 | 防御手段 |
|---|---|
| SQL 注入 | 参数化查询，永远不拼接 SQL 字符串 |
| XSS | 输出时转义 HTML 实体，CSP 头限制脚本执行 |
| SSRF | 限制内部网络访问，URL 白名单校验 |
| 文件上传 | 校验文件类型（不信任扩展名，检查 magic bytes）、限制大小、隔离存储 |
| JSON 解析 | 限制深度和大小，防止 JSON bomb |

### HTTP 安全头

| 头部 | 作用 |
|---|---|
| `Strict-Transport-Security` | 强制 HTTPS |
| `X-Content-Type-Options: nosniff` | 防止 MIME 类型嗅探 |
| `X-Frame-Options: DENY` | 防止点击劫持 |
| `Content-Security-Policy` | 限制资源加载来源 |
| `X-XSS-Protection: 0` | 禁用浏览器有 bug 的 XSS 过滤器 |
| `Referrer-Policy: strict-origin-when-cross-origin` | 控制 Referer 泄漏 |

### 密码安全

| 规范 | 标准 |
|---|---|
| 哈希算法 | bcrypt（成本因子 ≥ 12）或 argon2id |
| 禁用算法 | MD5、SHA-1、SHA-256（太快，容易暴力破解） |
| 密码强度 | ≥ 8 字符，检查是否在常见泄漏密码库中 |
| 登录失败锁定 | 5 次失败后锁定 15 分钟（按 IP + 账号组合） |

### 敏感数据处理

| 场景 | 处理 |
|---|---|
| 数据库 | 密码哈希存储、敏感字段加密存储 |
| 日志 | 密码、Token、身份证号、银行卡号绝不打印 |
| API 响应 | 密码字段不返回，身份证 / 手机号脱敏显示 |
| 传输 | 全链路 TLS 1.2+，内部服务间 mTLS |

## 负载测试

| 类型 | 目的 |
|---|---|
| **基准测试 (Benchmark)** | 正常负载下的性能数据，建立基线 |
| **负载测试 (Load Test)** | 逐步增加到预期峰值负载，验证系统承载能力 |
| **压力测试 (Stress Test)** | 超过设计容量，找到系统极限和瓶颈 |
| **浸泡测试 (Soak Test)** | 长时间稳定负载，发现内存泄漏等慢性问题 |

### 测试流程

1. 确定场景：哪些接口、什么比例、什么数据
2. 准备环境：和生产环境尽量一致的测试环境
3. 准备数据：足够量的测试数据（不是空库测试）
4. 逐步加压：从 10% 预期负载开始，每次增加 20-30%
5. 观察指标：QPS、延迟（p50/p95/p99）、错误率、资源使用率
6. 找到拐点：延迟开始指数级上升的点就是系统瓶颈
7. 输出报告：瓶颈在哪、最大承载量、优化建议

## 故障排查流程

1. **确认影响范围**：哪些服务、哪些用户、影响程度
2. **止血（先恢复服务，再找根因）**：
   - 回滚最近的发布
   - 切换到降级模式
   - 扩容应对流量
3. **定位根因**：
   - 看告警和监控面板 → 缩小范围
   - 看错误日志 → 找具体报错
   - 用 traceId 追踪请求链路 → 找到失败节点
4. **修复并验证**
5. **写事后复盘（Postmortem）**

## 常见错误

| 错误做法 | 正确做法 |
|---|---|
| 协程没有退出机制 | 用 `context.Context` 或关闭 Channel 透传取消 |
| Channel 操作无超时控制 | 用 `select` 加 `ctx.Done()` 超时分支 |
| `lock.Lock()` 后忘记 `defer Unlock` | 必须紧跟 `defer lock.Unlock()` |
| Double-checked Locking 做单例 | 用 `sync.Once` |
| 缓存击穿无互斥锁 | 用 `singleflight` 或 Redis 分布式锁保护 |
| 缓存雪崩 TTL 完全相同 | TTL + 随机扰动（0-300s） |
| 分布式锁 value 用固定值 | 每个实例 / 协程用唯一 UUID |
| 释放锁用 `DEL` 而非 Lua 脚本 | 用 Lua 脚本保证"校验+删除"原子性 |
| Access Token 寿命过长 | 15-30 分钟，配合 Refresh Token |
| 限流失败返回 500 | 返回 `HTTP 429` + `Retry-After` |
| 用 MD5 / SHA-256 存密码 | bcrypt（≥ 12）或 argon2id |
| 凭"猜"定位性能瓶颈 | 用火焰图 / 慢查询日志 / 堆内存分布数据定位 |
| 故障时先找根因 | 先止血（回滚 / 降级 / 扩容），再定位根因 |
