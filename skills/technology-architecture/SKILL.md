⚙️ 技术架构（Technology Architecture）
核心问题：系统跑在什么上面？如何保障运行质量？如何应对规模增长？


📌 职责范围
  基础设施（Infrastructure）        ——  计算、存储、网络的选型和拓扑
  云原生（Cloud Native）            ——  容器化、编排、服务网格、Serverless
  可靠性工程（SRE）                ——  SLI/SLO/SLA、容量规划、故障预案
  安全合规（Security & Compliance） ——  零信任、WAF、密钥管理、渗透测试
  DevOps & 工程效能                ——  CI/CD、IaC、可观测性、开发者体验


📌 基础设施分层（从底层到顶层）

  可观测性层（Observability）
    Metrics(Prometheus) · Logs(Loki/ELK) · Traces(Tempo/Jaeger)
        ↑
  服务治理层（Service Mesh / API Gateway）
    流量管理 · 熔断限流 · 灰度发布 · 链路追踪
        ↑
  应用运行时层（Container Orchestration）
    Kubernetes · 弹性伸缩 · 滚动更新 · 健康检查
        ↑
  数据持久层（Data Persistence）
    数据库集群 · 缓存集群 · 消息队列 · 对象存储
        ↑
  基础资源层（IaaS / Cloud）
    VPC · 子网 · 安全组 · 负载均衡 · DNS


📌 容量估算

  快速估算公式：
    日请求量 = DAU × 人均操作数
    平均 QPS = 日请求量 / 86400
    峰值 QPS = 平均 QPS × 3（假设高峰集中在 4 小时）
    年存储量 = 日请求量 × 单请求数据量 × 365

  示例：电商系统
    DAU: 500,000  人均操作: 20
    日请求量: 10,000,000
    峰值 QPS: 347
    年存储（按 2KB/请求）: 6.8 TB

  估算原则：
    先估数量级，再细化（10x 误差通常可接受）
    峰值按平均值的 3-10 倍设计（看业务特征）
    预留 30% 余量应对增长
    每季度复核一次容量计划


📌 可靠性设计

  SLI / SLO / SLA 框架：
    SLI（指标）：衡量服务健康的具体指标
      例：请求延迟 p99、错误率、可用性百分比
    SLO（目标）：对 SLI 设定的内部目标
      例：p99 延迟 < 200ms、月可用性 > 99.95%
    SLA（协议）：对外承诺，违反有赔偿
      例：月可用性 > 99.9%，否则赔偿 10% 月费

    原则：SLO 要比 SLA 严格（留安全余量）
    原则：不是所有服务都需要四个9，按业务重要性分级

  可用性等级速查：
    99%（两个9）    → 年停机 3.65 天     → 内部工具
    99.9%（三个9）  → 年停机 8.77 小时   → 一般 ToB 产品
    99.95%          → 年停机 4.38 小时   → 核心业务系统
    99.99%（四个9） → 年停机 52.6 分钟   → 支付、交易系统
    99.999%（五个9）→ 年停机 5.26 分钟   → 关键基础设施（极少需要）

  弹性设计模式：

    超时
      设置合理的超时时间（不要用默认的无限等待）
      上游超时 > 下游超时（避免上游还在等，下游已经重试了）

    重试
      指数退避 + 抖动（exponential backoff + jitter）
      只重试幂等操作
      设置最大重试次数（通常 3 次）
      区分可重试错误（超时、503）和不可重试错误（400、403）

    熔断
      快速失败，避免级联雪崩
      三态：关闭 → 打开（失败率 > 阈值） → 半开（探测恢复）
      熔断打开时走降级逻辑

    降级
      返回缓存数据 / 默认值 / 简化功能
      例：推荐服务不可用 → 返回热销排行榜
      降级策略要提前设计和测试，不能临时拍脑袋

    隔离（舱壁模式 Bulkhead）
      每个下游依赖独立线程池/连接池
      一个下游挂了不影响其他
      例：支付通道 A 超时不应影响查询订单的能力

    限流
      令牌桶 / 漏桶 / 滑动窗口
      区分用户等级，VIP 用户更高配额
      在 API 网关层统一实施


📌 CI/CD 与工程效能

  理想的部署流水线：
    代码提交 → 静态分析 → 单元测试 → 构建镜像 → 集成测试
    → 推送到镜像仓库 → 部署到 Staging → 自动化回归测试
    → 灰度发布（金丝雀/蓝绿）→ 监控指标 → 全量发布
    → 异常时自动回滚

  发布策略：
    滚动更新：逐步替换旧实例，最简单，适合无状态服务
    蓝绿部署：两套环境切换，回滚快，但资源消耗翻倍
    金丝雀发布：先导 1-5% 流量到新版本，观察指标再逐步放量
    特性开关：代码层面控制功能开关，部署和发布解耦

  DORA 关键指标：
    部署频率        精英：按需/每天       中等：每周~每月
    变更前置时间     精英：< 1 天         中等：1 周~1 月
    变更失败率       精英：< 5%          中等：15%~30%
    故障恢复时间     精英：< 1 小时       中等：1 天~1 周

  基础设施即代码（IaC）：
    所有基础设施通过代码定义（Terraform / Pulumi / CloudFormation）
    基础设施变更走 PR 流程，和代码一样 review
    环境可复现：从代码能重建完整环境
    禁止手动修改生产环境配置


📌 安全架构（Defense in Depth）

  1. 边界安全
    WAF（Web 应用防火墙）
    DDoS 防护
    CDN + 边缘安全策略

  2. 网络安全
    VPC 隔离 + 安全组
    零信任网络（服务间 mTLS）
    网络策略（限制 Pod 间通信）

  3. 应用安全
    认证：OAuth 2.0 / OIDC / JWT
    授权：RBAC + ABAC
    输入校验：防 SQL 注入、XSS
    API 安全：限流、签名、版本控制

  4. 数据安全（与数据架构 Skill 联动）
    传输加密：TLS 1.3
    存储加密：AES-256 / 信封加密
    密钥管理：KMS / Vault
    数据脱敏：动态脱敏 + 静态脱敏

  5. 运维安全
    最小权限原则
    审计日志全覆盖
    密钥/凭证轮换自动化
    定期渗透测试 + 漏洞扫描


📌 可观测性三支柱

  Metrics（指标）
    系统指标：CPU、内存、磁盘、网络
    应用指标：QPS、延迟分布（p50/p95/p99）、错误率
    业务指标：订单量、支付成功率、注册转化率
    工具：Prometheus + Grafana

  Logs（日志）
    结构化日志（JSON 格式），包含 traceId
    日志分级：DEBUG / INFO / WARN / ERROR
    集中采集，统一检索
    工具：ELK / Loki + Grafana

  Traces（链路追踪）
    跨服务调用的完整链路可视化
    每个请求有全局唯一的 traceId
    自动采集 span，支持手动埋点
    工具：Jaeger / Tempo / Zipkin

  告警设计：
    基于 SLO 设置告警，不是基于资源使用率
    告警必须有 Runbook（收到告警后怎么处理）
    分级：P0（立即响应）/ P1（1小时内）/ P2（当天）/ P3（本周）
    避免告警疲劳：宁可少几条精准的，不要多几百条没人看的


📌 技术选型决策矩阵模板

  维度            权重    方案 A    方案 B    方案 C
  功能匹配度      30%    评分1-10  评分1-10  评分1-10
  性能/扩展性     20%
  运维复杂度      15%
  团队熟悉度      15%
  社区/生态成熟度  10%
  成本（TCO）     10%
  加权得分

  使用说明：
    权重根据业务阶段调整（早期团队熟悉度权重更高，规模化后扩展性权重更高）

    差距 < 10% 时，选团队更熟悉的
    记录结果到 ADR（与应用架构 Skill 联动）


📌 技术架构反模式

  过度工程化
    症状：日活 1000 的系统用了 K8s + 服务网格 + 分布式追踪全家桶
    解药：按实际规模选型，单机能扛的就别分布式

  监控盲区
    症状：出了问题靠用户反馈、靠猜
    解药：可观测性三支柱：Metrics + Logs + Traces

  手动部署
    症状：部署靠 SSH 登录手动操作，每次都像在拆炸弹
    解药：CI/CD 自动化 + 基础设施即代码（IaC）

  密码硬编码
    症状：数据库密码写在配置文件里提交到 Git
    解药：使用 Vault / KMS / 环境变量注入

  单点故障
    症状：架构图上画了一个没有冗余的组件
    解药：关键路径上的每个组件都需要冗余方案

  云供应商锁定
    症状：深度使用某一家云的私有 API，迁移成本极高
    解药：核心逻辑与云厂商解耦，用抽象层隔离

  告警风暴
    症状：一个故障触发 200 条告警，团队麻木后开始忽略
    解药：告警聚合 + 根因关联 + 定期清理无效告警
