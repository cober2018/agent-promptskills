# 技术架构

## 概述

系统跑在什么上面？如何保障运行质量？**技术架构不是堆技术名词，而是按业务规模做"刚刚好"的选择。**

## 何时使用

- 基础设施分层（IaaS / 数据 / 运行时 / 服务治理 / 可观测性）
- 容量估算（QPS、存储、峰值）
- SLI / SLO / SLA 框架设计
- 弹性设计模式（超时、重试、熔断、降级、隔离、限流）
- 技术选型决策矩阵
- 反模式识别（过度工程化、监控盲区、单点故障等）

**不要用于：** 具体数据库表结构（用 `database-engineering`）、CI/CD 流水线配置（用 `cicd-engineering`）、监控告警搭建（用 `observability-ops`）、API 安全细节（用 `system-reliability`）。

## 职责范围

| 领域 | 内容 |
|---|---|
| **基础设施** | 计算、存储、网络的选型和拓扑 |
| **云原生** | 容器化、编排、服务网格、Serverless |
| **可靠性工程** | SLI / SLO / SLA、容量规划、故障预案 |
| **安全合规** | 零信任、WAF、密钥管理、渗透测试 |
| **DevOps & 工程效能** | CI/CD、IaC、可观测性、开发者体验 |

## 基础设施分层（从底层到顶层）

| 层级 | 技术组件 |
|---|---|
| **可观测性层** | Metrics (Prometheus) · Logs (Loki/ELK) · Traces (Tempo/Jaeger) |
| **服务治理层** | 服务网格 / API Gateway：流量管理 · 熔断限流 · 灰度发布 · 链路追踪 |
| **应用运行时层** | Kubernetes · 弹性伸缩 · 滚动更新 · 健康检查 |
| **数据持久层** | 数据库集群 · 缓存集群 · 消息队列 · 对象存储 |
| **基础资源层** | VPC · 子网 · 安全组 · 负载均衡 · DNS |

## 容量估算

### 快速估算公式

| 指标 | 公式 |
|---|---|
| 日请求量 | `DAU × 人均操作数` |
| 平均 QPS | `日请求量 / 86400` |
| 峰值 QPS | `平均 QPS × 3`（假设高峰集中在 4 小时） |
| 年存储量 | `日请求量 × 单请求数据量 × 365` |

### 估算示例（电商系统）

| 指标 | 数值 |
|---|---|
| DAU | 500,000 |
| 人均操作 | 20 |
| 日请求量 | 10,000,000 |
| 峰值 QPS | 347 |
| 年存储（2KB/请求） | 6.8 TB |

### 估算原则

| 原则 | 说明 |
|---|---|
| 先估数量级 | 再细化，10x 误差通常可接受 |
| 峰值设计 | 按平均值的 3-10 倍设计（看业务特征） |
| 预留余量 | 预留 30% 余量应对增长 |
| 季度复核 | 每季度复核一次容量计划 |

## 可靠性设计

### SLI / SLO / SLA 框架

| 概念 | 含义 | 示例 |
|---|---|---|
| **SLI（指标）** | 衡量服务健康的具体指标 | 请求延迟 p99、错误率、可用性百分比 |
| **SLO（目标）** | 对 SLI 设定的内部目标 | p99 延迟 < 200ms、月可用性 > 99.95% |
| **SLA（协议）** | 对外承诺，违反有赔偿 | 月可用性 > 99.9%，否则赔偿 10% 月费 |

**关键原则：** SLO 要比 SLA 严格（留安全余量）；不是所有服务都需要四个 9，按业务重要性分级。

### 可用性等级速查

| 等级 | 年停机 | 适用 |
|---|---|---|
| 99%（两个 9） | 3.65 天 | 内部工具 |
| 99.9%（三个 9） | 8.77 小时 | 一般 ToB 产品 |
| 99.95% | 4.38 小时 | 核心业务系统 |
| 99.99%（四个 9） | 52.6 分钟 | 支付、交易系统 |
| 99.999%（五个 9） | 5.26 分钟 | 关键基础设施（极少需要） |

## 弹性设计模式

### 超时

| 原则 | 说明 |
|---|---|
| 合理超时 | 设置合理的超时时间（不要用默认的无限等待） |
| 上下游协调 | 上游超时 > 下游超时（避免上游还在等，下游已经重试了） |

### 重试

| 原则 | 说明 |
|---|---|
| 退避策略 | 指数退避 + 抖动（exponential backoff + jitter） |
| 幂等性 | 只重试幂等操作 |
| 最大次数 | 设置最大重试次数（通常 3 次） |
| 错误分类 | 区分可重试错误（超时、503）和不可重试错误（400、403） |

### 熔断

| 原则 | 说明 |
|---|---|
| 快速失败 | 避免级联雪崩 |
| 三态 | 关闭 → 打开（失败率 > 阈值）→ 半开（探测恢复） |
| 降级 | 熔断打开时走降级逻辑 |

### 降级

| 策略 | 示例 |
|---|---|
| 返回缓存数据 / 默认值 | 推荐服务不可用 → 返回热销排行榜 |
| 提前设计 | 降级策略要提前设计和测试，不能临时拍脑袋 |

### 隔离（舱壁模式 Bulkhead）

| 原则 | 说明 |
|---|---|
| 独立资源 | 每个下游依赖独立线程池 / 连接池 |
| 故障隔离 | 一个下游挂了不影响其他（如支付通道 A 超时不应影响查询订单） |

### 限流

| 原则 | 说明 |
|---|---|
| 算法 | 令牌桶 / 漏桶 / 滑动窗口 |
| 用户分级 | 区分用户等级，VIP 用户更高配额 |
| 实施层 | 在 API 网关层统一实施 |

## 技术选型决策矩阵模板

| 维度 | 权重 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|---|
| 功能匹配度 | 30% | 评分 1-10 | 评分 1-10 | 评分 1-10 |
| 性能 / 扩展性 | 20% | | | |
| 运维复杂度 | 15% | | | |
| 团队熟悉度 | 15% | | | |
| 社区 / 生态成熟度 | 10% | | | |
| 成本（TCO） | 10% | | | |
| **加权得分** | — | | | |

**使用说明：**

| 原则 | 说明 |
|---|---|
| 权重调整 | 根据业务阶段调整（早期团队熟悉度权重更高，规模化后扩展性权重更高） |
| 评分依据 | 评分必须有依据，不能拍脑袋 |
| 接近时选择 | 差距 < 10% 时，选团队更熟悉的 |
| 决策记录 | 记录结果到 ADR（与应用架构 Skill 联动） |

## 技术架构反模式

| 反模式 | 症状 | 解药 |
|---|---|---|
| **过度工程化** | 日活 1000 的系统用了 K8s + 服务网格 + 分布式追踪全家桶 | 按实际规模选型，单机能扛的就别分布式 |
| **监控盲区** | 出了问题靠用户反馈、靠猜 | 可观测性三支柱：Metrics + Logs + Traces |
| **手动部署** | 部署靠 SSH 登录手动操作，每次都像在拆炸弹 | CI/CD 自动化 + 基础设施即代码（IaC） |
| **密码硬编码** | 数据库密码写在配置文件里提交到 Git | 使用 Vault / KMS / 环境变量注入 |
| **单点故障** | 架构图上画了一个没有冗余的组件 | 关键路径上的每个组件都需要冗余方案 |
| **云供应商锁定** | 深度使用某一家云的私有 API，迁移成本极高 | 核心逻辑与云厂商解耦，用抽象层隔离 |
| **告警风暴** | 一个故障触发 200 条告警，团队麻木后开始忽略 | 告警聚合 + 根因关联 + 定期清理无效告警 |

## 常见错误

| 错误做法 | 正确做法 |
|---|---|
| 上游超时 < 下游超时 | 上游超时 > 下游超时 |
| 重试非幂等操作 | 只重试幂等操作 |
| 重试无最大次数 | 设置最大重试次数（通常 3 次） |
| 熔断后无降级逻辑 | 熔断打开时走降级逻辑 |
| 业务重要性与 SLO 不匹配 | 核心业务 SLO 严格，内部工具 SLO 可放宽 |
| 容量估算无余量 | 峰值 3-10x + 30% 余量 |
| 容量计划一年不复核 | 每季度复核 |
| 反模式识别后无 ADR 记录 | 所有重大技术决策写 ADR |
| 选型时差距 5% 选陌生的 | 差距 < 10% 选团队更熟悉的 |
| 监控仅看资源指标 | 必须看 SLO 指标（延迟、错误率、可用性） |
