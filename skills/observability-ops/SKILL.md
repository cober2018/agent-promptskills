📡 可观测性运维（Observability & Operations）
核心问题：系统现在健康吗？出了问题能多快发现？能多快恢复？


📌 可观测性三支柱

  Metrics（指标）：
    基础设施指标：CPU、内存、磁盘、网络
    应用指标：QPS、延迟分布（p50/p95/p99）、错误率
    业务指标：订单量、支付成功率、注册转化率
    工具：Prometheus + Grafana
    采集方式：应用暴露 /metrics 端点，Prometheus 定时拉取
    保留策略：高精度 15 天，降采样后保留 1 年

  Logs（日志）：
    格式：结构化 JSON
    必须包含：timestamp、level、traceId、service、message
    日志分级：
      DEBUG → 开发调试用，生产环境默认关闭
      INFO → 正常业务流程的关键节点
      WARN → 需要关注但不影响功能的异常
      ERROR → 需要处理的错误，触发告警
    敏感信息：密码、Token、身份证号绝对不进日志
    工具：ELK（Elasticsearch + Logstash + Kibana）或 Loki + Grafana
    保留策略：热存储 30 天，冷存储 1 年

  Traces（链路追踪）：
    跨服务调用的完整链路可视化
    每个请求有全局唯一的 traceId
    自动采集 span，支持手动埋点关键业务节点
    工具：Jaeger / Tempo / Zipkin
    采样策略：生产环境采样率 1-10%（全量采集成本太高）
    错误请求 100% 采集（不采样）


📌 告警设计

  告警分级：
    P0（立即响应，5 分钟内）：
      核心服务完全不可用
      数据一致性问题
      安全事件（入侵、数据泄露）
      通知：电话 + 短信 + 钉钉/飞书

    P1（1 小时内响应）：
      非核心服务异常
      性能严重退化（p99 > SLO 的 5 倍）
      错误率飙升（> 正常值的 10 倍）
      通知：钉钉/飞书 + 邮件

    P2（当天处理）：
      性能轻微退化
      磁盘空间预警（> 80%）
      证书即将过期（< 30 天）
      通知：钉钉/飞书

    P3（本周处理）：
      资源使用趋势预警
      非关键服务的偶现错误
      性能优化建议
      通知：每日汇总报告

  告警规则设计原则：
    基于 SLO 告警，不是基于资源阈值
      ❌ CPU > 80% 告警
      ✅ p99 延迟 > 500ms 持续 5 分钟告警
    设置告警窗口，避免瞬时抖动
      ❌ 错误率 > 1% 立即告警
      ✅ 错误率 > 1% 持续 3 分钟告警
    每条告警必须有 Runbook
    定期清理无效告警（每月审查）
    告警数量以"少而精"为目标

  告警抑制与聚合：
    同一服务同一类型告警合并（不要一个故障触发 200 条告警）
    下游依赖告警与上游故障关联（A 挂了导致 B 超时，只告 A）
    维护窗口期间静默告警


📌 Runbook 模板

  Runbook: [告警名称]

  告警含义：
    这条告警说明什么问题？影响范围是什么？

  排查步骤：
    1. 查看 Grafana Dashboard [链接]，确认指标异常范围
    2. 查看日志 [链接/命令]，搜索错误关键字
    3. 检查最近的部署记录 [链接]，是否有新版本发布
    4. 检查依赖服务状态 [链接/命令]
    5. 检查资源使用情况（CPU/内存/磁盘/连接数）

  恢复操作：
    场景 A：如果是最近发布导致
      → 回滚到上一个版本 [回滚命令]
    场景 B：如果是资源不足
      → 扩容 [扩容命令]
    场景 C：如果是依赖服务故障
      → 开启降级模式 [降级配置]

  升级路径：
    如果 15 分钟内未恢复 → 升级到 [团队负责人]
    如果 30 分钟内未恢复 → 升级到 [技术总监]

  历史案例：
    [日期]：[简述事故和解决方案]


📌 Dashboard 设计

  分层 Dashboard：

    全局概览（Overview）：
      所有服务的健康状态（绿/黄/红）
      全局错误率和延迟趋势
      关键业务指标（订单量、成功率）
      最近的部署和事件

    服务详情（Per-Service）：
      该服务的 QPS / 延迟 / 错误率
      资源使用（CPU / 内存 / 连接池）
      依赖服务的调用延迟和错误率
      最近的日志错误

    基础设施（Infrastructure）：
      节点健康状态
      Pod 分布和资源使用
      存储使用率
      网络流量

  Dashboard 设计原则：
    从上到下：概览 → 细节 → 根因
    从左到右：时间维度对齐，便于关联分析
    颜色一致：绿 = 正常，黄 = 预警，红 = 告警
    每个面板有说明文字，新人也能看懂


📌 事件响应

  事件响应流程：
    1. 发现（Detection）
       告警触发 / 用户报告 / 监控发现
       确认影响范围和严重程度
       指定事件指挥官（Incident Commander）

    2. 止血（Mitigation）
       目标：最快恢复服务，不是找根因
       回滚最近的部署
       切换到降级模式
       扩容应对流量
       记录所有操作和时间点

    3. 定位根因（Root Cause）
       看告警和监控面板 → 缩小范围
       看错误日志 → 找具体报错
       用 traceId 追踪请求链路 → 找到失败节点
       对比变更：最近的代码/配置/基础设施变更

    4. 修复并验证
       修复根因
       验证修复有效
       确认告警恢复
       观察一段时间确保稳定

    5. 事后复盘（Postmortem）
       事件概要：什么时间、影响了什么、持续多久
       时间线：从发现到恢复的每个关键动作和时间点
       根因分析：直接原因 + 根本原因（用 5 Whys）
       修复措施：已做的和计划做的
       经验教训：我们学到了什么、如何防止再次发生
       行动项：具体的改进任务、责任人、截止日期

  事件响应原则：
    先恢复服务，再找根因
    所有操作都记录时间线（事后复盘的素材）
    不追责个人，追责流程和系统
    每次事故都产出至少一个改进行动项


📌 自愈系统

  自动恢复机制：
    K8s livenessProbe 失败 → 自动重启容器
    K8s readinessProbe 失败 → 自动移出流量
    HPA 自动扩缩容 → 根据 CPU/自定义指标
    PDB 保护 → 维护时保证最低可用 Pod 数

  自愈规则设计：
    重启次数限制：CrashLoopBackOff 超过 5 次 → 停止重启 + 告警人工介入
    扩容上限：设置 maxReplicas 防止无限扩容（成本失控）
    降级开关：依赖服务不可用时自动切换到降级逻辑

  混沌工程（进阶）：
    定期模拟故障验证自愈能力
    随机杀 Pod：验证服务冗余
    注入延迟：验证超时和降级策略
    断开依赖：验证隔离和容错
    在非高峰期执行，有快速停止的能力
