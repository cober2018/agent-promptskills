# 4A 协同工作流（Architecture Collaboration Workflow）

> 权威源（Authoritative Source）
> 本文件是 4A（Business / Application / Data / Technology）协同的**唯一权威源**。
> 所有 4A 相关 agent 的提示词（`4a-architect` 及未来接入的架构类 agent）只承载必须自检的硬约束，**不再内联** 4A 流程、清单或模板，避免与本文件漂移。
> 提示词与本文冲突时，**以本文为准**。

## 1. 4A 分层定义

四层自上而下，**单向依赖，禁止反向调用**：

| 层 | 关注点 | 主要产物 | 典型 Agent / 团队 |
|---|---|---|---|
| Business 业务架构 | 价值流、能力地图、康威定律 | 业务能力地图、价值流图 | `business-architecture` skill、`product` 团队 |
| Application 应用架构 | 服务边界、API 契约、集成模式 | 服务清单、OpenAPI / Protobuf 契约、ADR | `application-architecture` skill、`backend-engineer` |
| Data 数据架构 | 领域模型、主数据、数据流 | 概念 / 逻辑 / 物理模型、Medallion 分层 | `data-architecture` skill、`data-engineer` |
| Technology 技术架构 | 基础设施、运行时、安全合规 | IaC、SLI/SLO、零信任策略 | `technology-architecture` skill、`devops-engineer` |

> 说明：`qa-engineer` 与 `devops-engineer` 是交付期的横切角色，不构成新的 4A 层。具体任务归属、交付协作流与反例以 `docs/standards/agent-delivery-responsibility-routing.md` 为准。

## 2. 能力域判定规则

在提出任何架构变更建议前，先回答两个问题：

1. **本次工作主要落在哪一层？** 给出明确的层（Business / Application / Data / Technology），如果跨多层则全部列出并指明主层。
2. **本次工作触发的是哪种边界变更？** 至少识别以下四类之一：
   - 跨服务调用边界
   - 跨能力域边界（业务 ↔ 应用 ↔ 数据 ↔ 技术）
   - 跨存储边界（OLTP / OLAP / 缓存 / 消息 / 文件）
   - 跨调度边界（同步 / 异步 / 批 / 流）

判定结果必须写在架构输出的**最前段**，作为后续清单与 ADR 的依据。

## 3. 硬约束（Agent 自检项）

以下五项是任何架构输出的最低要求，**任一项缺失即视为回答不完整**：

1. **能力域先识别** —— 显式声明本次工作的 4A 主层与涉及的其它层。
2. **运行时归属与单一事实源** —— 写出涉及的运行时（服务进程、调度器、存储集群、API 网关、配置中心等）、归属团队或 agent，并指明本次事实 / 数据 / 契约的单一权威源（哪份文档、哪张表、哪段配置）。
3. **边界变更 → ADR + 文档同步** —— 跨服务、跨域、跨存储、跨调度、跨能力域的边界变更，**先**写或更新 ADR（`docs/adr/`）与对应 standards / 架构文档，**再**提交代码。
4. **调度 / 存储边界 / 跨域三场景清单必跑** —— 涉及调度器、存储边界、跨能力域任一场景时，按 §6 架构评审清单逐项核对，并在结论中显式给出每项判定。
5. **流程以本文档为准** —— agent 提示词与本文冲突时以本文为准；不要把本文档全文粘贴到答案中，只引用条款编号或标题。

## 4. ADR 模板

`docs/adr/NNNN-<slug>.md`，命名四位递增编号 + 小写连字符 slug。**强制字段**：

| 字段 | 必填 | 说明 |
|---|---|---|
| 标题 | ✅ | 决策一句话陈述，动词化（如「采用 X」「放弃 Y」） |
| 状态 | ✅ | `Proposed` / `Accepted` / `Deprecated` / `Superseded` |
| 日期 | ✅ | RFC3339 生效日 |
| 背景 | ✅ | 痛点、约束、利益相关方；说明「为什么现在要做」 |
| 决策 | ✅ | 一句话陈述最终选择 |
| 备选 | ✅ | ≥ 2 个备选方案，附各自的优劣与放弃原因 |
| 权衡 | ✅ | 已选方案的正向收益 + 已接受的代价 |
| 后果 | ✅ | 短期 / 长期影响、对其他 ADR / 文档的联动 |
| 正文链接 | ⭕ | 相关 RFC / 文档 / 代码 PR / 监控看板 |

## 5. 边界变更触发条件

满足以下任一条件，**必须**走 ADR 流程：

- 新增 / 删除 / 拆分 / 合并服务
- 新增 / 替换 / 退役数据库、消息队列、缓存、对象存储
- 新增 / 替换调度器、调度策略、JobStore
- 跨能力域数据流（业务→技术、数据→应用 等）
- 跨团队的 API 契约变更
- 引入新的认证 / 授权 / 审计路径
- 调整 SLI / SLO 目标

## 6. 架构评审清单

### 6.1 通用清单（任何架构输出必跑）

- [ ] 是否解决了 §2 已识别的业务痛点？
- [ ] 备选方案是否 ≥ 2 个？是否在 ADR 中说明取舍？
- [ ] 与现有 4A 分层是否一致？是否引入新的耦合？
- [ ] 容量与可用性目标是否量化（QPS、p99、可用性）？
- [ ] 安全与合规是否过审（数据分级、跨境、密钥）？
- [ ] 是否有可演进的路径（Strangler Fig / 灰度）？
- [ ] ADR 链接是否到位？单一事实源是否声明？

### 6.2 调度场景清单（涉及调度器时追加）

- [ ] JobStore 选型是否明确（MongoDB / Redis / SQL / 内存）？重启 / 漂移 / 多实例行为是否说明？
- [ ] 调度命令面（API / RPC）与执行面（Worker）是否解耦？是否走 Redis PubSub 或等价消息总线？
- [ ] 任务注册的 PreFlight / 校验链是否覆盖（脚本可编译、依赖就绪、目标表存在）？
- [ ] 失败重试策略是否声明（最大次数、退避、熔断、告警分级）？
- [ ] 漂移检测（MongoDBJobStore vs in-memory state）是否定期跑？

### 6.3 存储边界清单（涉及跨存储或新存储选型时追加）

- [ ] 数据契约是否定义（schema、SLA、上下游、保留期）？
- [ ] 写入路径是否幂等？重复写入是否会破坏业务语义？
- [ ] 读取路径是否分冷热（OLAP / OLTP / 缓存）？是否会穿透到 OLTP？
- [ ] 数据血缘是否可追踪（采集脚本 → 表 → 看板 / 因子 / 模型）？
- [ ] 数据分级（公开 / 内部 / 机密）是否标注？跨境 / 跨域传输是否过审？
- [ ] 归档 / 清理策略是否量化（保留期、分区策略、删除机制）？

### 6.4 跨能力域清单（涉及 ≥ 2 层时追加）

- [ ] 主层与副层是否显式声明？副层是否仅为「被通知方」而非「共同决策方」？
- [ ] 跨层契约是否走 OpenAPI / Protobuf / 数据契约，禁止跨层直连数据库 / 直读消息？
- [ ] 跨层变更是否同时更新双方 standards 文档与 ADR？
- [ ] 是否触发康威定律反向调整（团队边界 / 代码仓归属）？

### 6.5 交付协作清单（涉及任务分派、实现协作或发布验收时追加）

- [ ] 主责实现 agent 是否唯一（`frontend-engineer` / `backend-engineer` / `data-engineer` / `devops-engineer` / `qa-engineer`）？
- [ ] 是否区分了「调度平台问题」与「调度器承载的任务问题」？
- [ ] 若调度器正常，任务脚本 / SQL / 表写入 / DQC / 指标或因子逻辑是否归 `data-engineer` 主责？
- [ ] 发布、部署、监控、回滚是否显式纳入 `devops-engineer`？
- [ ] 测试设计、执行证据、发布建议是否显式纳入 `qa-engineer`？

## 7. 文档关系

| 文档 | 关系 |
|---|---|
| `4a-architect` agent prompt | **引用**本文档；只承载 §3 五条硬约束，不内联流程 |
| `docs/standards/agent-delivery-responsibility-routing.md` | 开发期 agent 职责路由权威源；本文件 §6.5 引用其结论 |
| `docs/adr/NNNN-*.md` | **遵循** §4 模板；由 §5 边界变更触发 |
| `docs/standards/AGENT_SCHEDULER_GUIDE.md` | 调度器的事实源；本文件 §6.2 引用其结论 |
| `docs/standards/数据仓库架构文档.md` | 数仓的事实源；本文件 §6.3 引用其结论 |
| `openspec/changes/**` | 业务级变更提案；与本文件互为补充，跨边界变更需同时走 ADR |

## 8. 演进规则

- 本文件变更必须先提 ADR（`docs/adr/`，分类属于「流程治理」类）。
- 6 个月内的条款可经一次架构委员会复盘重审；1 年以上未复盘的条款视为过期。
- 新增架构类 agent 必须**先**接入本文件，再写 agent prompt，禁止内联 4A 流程。
